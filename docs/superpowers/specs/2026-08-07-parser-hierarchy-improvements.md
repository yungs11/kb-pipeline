# 이미지 파서 구조 개선 포인트 — 계층(문맥구조) 실측 기반

> 작성 2026-08-07. 근거: 업무문서 실측 3회차(1·2차 18건/80페이지 완료, 3차 50건 진행 중)를
> **계층 보존 기준**으로 전수 재검증한 결과. 원 데이터·페이지별 3-way 비교본은 세션
> scratchpad(`triage-tuning-2026-08-06/`)에 있고, 요약은 같은 폴더 `RECOMMENDATIONS_v2.md`.
>
> **이 문서는 임계치 튜닝이 아니라 구조 개선 항목이다.** 임계치(env)로 풀리는 문제와
> 구조를 바꿔야 풀리는 문제를 가르는 것이 핵심 — 아래 P1~P5 는 전부 후자다.
> 각 항목은 **별건 plan + ultracode 검증**을 거쳐 구현한다(이 문서는 착수 근거만 제공).

## 왜 이 문서가 필요한가

사용자 정의로 "상위-하위 개념"은 셋을 모두 포함한다 — ① 문서 헤딩(장/절/조) ② **표 병합셀의
상하위**(그룹 헤더가 하위 컬럼을 거느림) ③ **도형/다이어그램의 상하위·단계 구조**(ABL
온톨로지 아키텍처도 같은 포함·단계 관계). 셋 다 "읽어서 문맥구조를 이해할 수 있어야" RAG
적재 가치가 있다.

실측 결과 **계층 종류마다 승자가 다르다**:

| 계층 종류 | 승자 | 근거(1·2차 80페이지) |
|---|---|---|
| 문서 헤딩 | **GW** | 헤딩 있는 54p 중 GW 46p / ODL 27p / VL 1p. 재현율 GW 90%+ vs ODL 40~50% |
| 표 병합 상하위 | **페이지 유형별** | 스캔 밀집표=GW(2단헤더 유일 보존) / 네이티브=ODL(거짓 행관계 없음) |
| 도형 상하위·단계 | **VL** | 화살표(→) 흐름서술 VL 43건, ODL·GW 0건 |

현재 구조는 **레인 하나가 이 셋을 다 결정**한다. 그래서 어떤 레인을 골라도 두 가지는 잃는다 —
이것이 근본 한계이고, 아래 개선의 출발점이다.

---

## P1. 헤딩 레벨을 텍스트 패턴으로 재계산 (최우선)

**문제**: 세 엔진 **모두** 깊이 계층을 못 준다.
- GW: 장(章)과 조(條)를 똑같이 `##` 로 평탄화 — "헤딩 존재" 지표는 이겨도 깊이는 없다.
- ODL: 정합 사례는 있으나 상위 헤딩을 놓쳐 **고아 레벨**이 생긴다(`1.1` 은 냈는데 부모 `1.` 누락).
- pptx 에서 GW 는 **부모/자식 레벨 역전**(부모 `###`, 자식 `##`)까지 낸다.

**개선**: 엔진이 준 `#` 개수를 그대로 믿지 말고, blockify 단계에서 텍스트 패턴으로 레벨을
덮어쓴다.
```
문서제목(첫 페이지 최상단)   → H1
"제N장"                       → H2
"제N절" / "제N관"             → H3
"제N조"                       → H4
"N.N" / "N.N.N"               → 점 개수 + 2
```
**효과**: GW 평탄화·ODL 고아레벨·pptx 역전이 **한 번에** 해결된다. 엔진 무관하게 계층이
일관돼 레인 선택과 계층 품질이 분리된다.

**비용/리스크**: `kb_pipeline/blockify.py` 에 정규식 후처리 1개. 패턴 미매치 시 기존 값을
유지하면 회귀 위험이 낮다. 단 **한국어 법률/규정 문서 관례에 특화**된 규칙이므로, 다른
문서 유형(영문·기술문서)에서 오작동하지 않는지 확인이 필요하다.

## P2. ODL 스캔PDF 헤딩 오염 차단

**문제**: 스캔 PDF 에서 ODL 이 `# - 1 -`(페이지번호)을 **헤딩으로** 출력한다. 실측
`naegyu_pdf_risk` p1·p2·p3·p5 에서 진짜 헤딩 0개인데 가짜 헤딩 4개 — KB 계층이 페이지번호로
오염된다. 같은 페이지에서 GW 는 `## 리스크관리규정`·`## 제1장 총 칙`·`## 제2절 위험관리책임자`
를 정확히 냈다.

**개선**: 헤딩 승격 전 필터 — 후보가 `^[-\s]*\d+[-\s]*$` 이거나 5자 미만 숫자성 문자열이면
헤딩으로 올리지 않고 일반 텍스트로 둔다.

**비용/리스크**: 정규식 1줄. 리스크 매우 낮음(진짜 헤딩이 "3" 한 글자인 경우는 없다).

## P3. 표 정본을 페이지 유형별로 분기

**문제**: 지금은 레인이 표까지 결정하는데, 실측상 정본이 갈린다.
- **스캔 밀집표**(등기부등본·원가내역·위임장) → **GW 정본**. rowspan+colspan 2단 헤더를
  동시에 보존하는 유일한 엔진. VL 은 체계적으로 붕괴(5컬럼→2컬럼, 병합 0개, rowspan 유실),
  ODL 은 스캔 표에 **기여 0**(10개 표 페이지 중 6개에서 표 0개).
- **네이티브 디지털**(결재란·사업개요) → **ODL 정본**. 병합 정확도는 3사 동등하지만 ODL 만
  논리적으로 독립된 표를 분리 유지한다. GW/VL 의 "1표 통합"은 시각적으로는 충실하나
  무관한 두 박스를 합쳐 **거짓 행 관계**를 만든다(예: 전화번호 박스와 기안결재 박스를 합쳐
  "팀원 3490-5893 | 03.13" 같은 행 생성).
- **VL 은 표 정본에서 제외**. 단순표에서만 동등하고 복잡해질수록 붕괴하며, pipe-표 이탈
  (CLAUDE.md 불변식 위반) 3건이 VL 에서만 나왔다.

**개선**: `_supplement_diagram_pages` 에 이미 있는 "paddle 표를 정본으로 백필" 패턴을 확장해,
페이지 유형(스캔 vs 네이티브)에 따라 표 블록의 출처를 고른다.

**비용/리스크**: 중간. 레인 결과를 합성하는 구조라 §A4(Plan A) 급 설계가 필요하고, additive
모드에서 중복이 생기지 않게 하는 가드가 필수다(v4 검증에서 이미 겪은 함정).

## P4. VL 환각 방어 — 교차검증 게이트

**문제(가장 위험)**: 저품질 스캔에서 VL 이 **그럴듯한 날조**를 한다. 실측
`sojang_yongin_p20`: 실제 페이지는 제7·9·11·13조가 불규칙하게 섞인 저품질 스캔인데, VL 은
**제7조~제25조를 일련번호대로 깔끔하게 생성**했다(존재하지 않는 서명란 포함, 보일러플레이트
19개). GW 의 깨진 OCR 은 쓰레기임이 즉시 보이지만 **VL 산출물은 그럴듯해서 사람이 검수해도
검출이 어렵다** — RAG 에 적재되면 근거 없는 조문이 검색 결과로 나온다.

**개선(최소)**: VL 결과를 GW/ODL 과 대조해 이상 신호가 있으면 폐기 후 GW 폴백.
- 길이가 비정상적으로 큼(예: 2배 이상)
- 조문/항목 번호가 **연속적**인데 다른 엔진에서는 불연속
- 다른 엔진이 낸 고유명사/숫자가 VL 에 전혀 없음

**비용/리스크**: 중간. 오탐(정상적으로 VL 이 더 잘 뽑은 경우)을 죽이지 않도록 임계를
보수적으로 잡아야 한다. 폐기보다 **경고 로그 + 플래그**부터 시작하는 게 안전하다.

## P5. GW 실패율 대응 (선행 조건)

**문제**: 1·2차에서 GW 가 **10회 실패**(502 Bad Gateway·타임아웃). P1/P3 에서 GW 를 헤딩·표
정본으로 쓰려면 이 신뢰성이 선행돼야 한다.

**개선**: 재시도 정책(세션 초반에 논의됐으나 미구현). 502/타임아웃은 페이지 단위 재시도,
연속 실패 시 레인 폴백.

## 임계치로 못 푸는 것 (구조 개선이 답인 이유)

**스캔 페이지의 GW-vs-VL 선택은 트리아제 신호로 원천적으로 불가능하다.** 아래 셋이 전부
`char=0, imgcov=1.00` 으로 동일하게 잡힌다:
- 깨끗한 단일컬럼 본문 스캔 → GW 로 충분(자원 효율)
- 밀집 표 스캔 → GW 우위(2단 헤더 보존)
- 저품질 스캔 → **VL 금지**(환각 위험, P4)

임계치를 아무리 정교하게 조정해도 이 구분은 안 된다 — P3/P4 같은 **결과 기반 분기**가 답이다.

## 참고 — 이번에 이미 적용된 것(구조 개선 아님)

  `KBP_PROMPT_HIERARCHY_RULE` 로 소스 수정 없이 교체 가능. 실측: 적용 전 헤딩 0건 →
  적용 후 5건(계층 정확), 다이어그램 페이지에서 단계별 부서 하위항목까지 복원 확인.
- 순서도 조항(`KBP_PAGE_HYBRID_DIAGRAM_RULE`)에 "상하위(포함) 관계" 요구 추가.
