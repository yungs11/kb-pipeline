## D1. `hybrid_to_blocks` 가 인라인 강조(`**bold**`)를 대응 필드 없이 버린다

마크다운 → 블록 변환에서 **대부분의 마크업은 필드로 옮겨간다**. 강조만 갈 곳이 없다.

| 마크업 | 처분 | 보존 |
|---|---|---|
| `#` `##` `###` | `text_level: 1/2/3` | ✅ 구조로 보존 |
| `- ` `* ` `1. ` | 텍스트에 기호 복원 + `list_markers: ['-']` | ✅ **일부러 되살린다** (`blockify.py:149-154` — 휴가규정 각주 소실 사고 대응) |
| `---` | 드롭 | 순수 구분선, 의미 없음 |
| **`**굵게**`** | **드롭** | ❌ **대응 필드 없음** |

```
원문:  **OUTPUT**: 질의 패턴 리스트
블록:  OUTPUT: 질의 패턴 리스트
```

## 왜 문제인가

강조가 **레이블 역할**을 하는 문서가 실재한다. `자산신탁 온톨로지 PoC` p13 은
`**OUTPUT**: …` / `**주체**: …` 형태로 각 단계의 산출물·담당을 표시하는데,
평문이 되면 "OUTPUT" 이 본문인지 필드명인지 구분되지 않는다.

## 이번 머지가 만든 문제가 **아니다**

- **머지 전**: 가로형 문서는 문서수준 `vl` 레인 → 페이지당 통짜 text 블록 1개.
  VL 마크다운이 **원문 그대로** 남아 `#` 도 `**` 도 문자로 보였다(대신 청킹 단위가 없었다).
- **머지 후**: 페이지수준 `vl` 레인이 `hybrid_to_blocks` 를 타면서 파싱된다
  (블록 18 → 409, 청킹 단위 확보).

즉 **`hybrid_to_blocks` 의 기존 동작이 이 경로에도 적용된 것**이고,
odl 레인·paddle_gw 레인은 **원래부터** 이렇게 돌고 있었다.

## 그대로 두는 이유 (사용자 결정 2026-08-13)

1. **소비자가 없다.** 청킹(`hierarchy_path`)은 `text_level` 을 읽고, 검색·임베딩은 평문을
   쓴다. 강조를 실제로 소비하는 하류가 지금 없어, 고쳐도 값만 쌓인다.
2. **고치면 스키마가 갈라진다.** 세 레인이 같은 `hybrid_to_blocks` 를 쓰는데 한 곳만
   바꾸면 블록 계약이 레인마다 달라진다.
3. **문자 감소는 손실이 아니다.** V6 실측 — p13 에서 마크업 제거분을 빼고 공백 무시로 비교하면
   **유사도 98.18%, 후판이 오히려 +56자**. 빠진 실질 내용은 0이었다.

## 언제 다시 봐야 하나

- **강조를 읽는 소비자가 생길 때** — 예: 청킹이 "라벨: 값" 패턴을 필드로 추출하거나,
  검색이 강조 가중치를 쓸 때.
- 그때 선택지는 둘: 텍스트에 `**` 복원(`list_markers` 방식 — 단, 임베딩에 마커가 섞인다)
  또는 `emphasis` 필드 신설(스키마 확장).
